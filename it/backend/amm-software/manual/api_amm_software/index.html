API Amministrazione Software¶

Scopo¶

Documentazione completa delle API REST del modulo Amm. Software (Amministrazione). Questi endpoint gestiscono utenti (operatori), permessi individuali, profili reparto e lookup di supporto.

Contesto¶

Il modulo Amm. Software e' il pannello di controllo per l'amministratore di sistema. Permette di creare operatori, assegnare ruoli, configurare override di permessi per singolo utente e definire profili di accesso per reparto (unita' organizzativa).

Tutti gli endpoint richiedono autenticazione JWT con ruolo ADMIN (AdminAPIView). Post-cutover multi-face il check ADMIN delega a PermissionResolver.is_super_admin (binding SUPER_ADMIN su config.profili_accesso_bindings, profilo seed id 9100). L'endpoint lista utenti ha throttling search attivo (is_search_endpoint = True).

Le risposte seguono l'envelope standard { "data": {...}, "meta": {...} }.

Base URL: /api/v1/amm-software/

1. Utenti¶

1.1 GET /api/v1/amm-software/operatori/ -- Lista utenti¶

Restituisce la lista paginata degli operatori con filtri opzionali: la prima scheda dell'area «Accessi» (§1-bis). ⭐ Dal 2026-10-02 una riga e' una credenziale di categoria OPERATORE (script.fn_categoria_accesso, la regola che decide il tab), e la veste mostrata e' quella di riferimento (script.fn_veste_di_riferimento: l'accesa, altrimenti la spenta piu' recente). Ogni riga porta veste_attiva: un operatore disattivato resta in elenco col tipo OPERATORE e veste_attiva = false (R-DB-1: «disabilitato» si legge dallo stato, non dal ruolo).

Parametri query string:

Parametro Tipo Obbligatorio Descrizione
search string no Ricerca libera sulle colonne che il catalogo della lista anagrafiche.operatori accende per l'operatore (le decide il catalogo, non il codice: ricerca_full nella configurazione della lista). Sotto 3 caratteri non filtra (nessun 400). Ogni riga porta anche soggetto_ragione_sociale (ragione sociale completa del soggetto, null senza soggetto)
is_super_admin bool no Filtra sul binding SUPER_ADMIN: true/false; ogni altro valore è un 400 E_VALIDATION_INPUT (dal 2026-10-20: prima 1/yes/on = vero e tutto il resto falso, in silenzio)
unita_organizzativa_id int no Filtra per unita' organizzativa
is_active bool no Filtra per stato attivo della credenziale (stessa lettura di is_super_admin)
includi_di_prova bool no true mostra anche gli utenti di prova (etichetta del provisioning di sviluppo); assente o false li nasconde. Booleano rigoroso: un valore non booleano e' un 400 sul campo
limit int no Numero massimo risultati (default 25, max 200)
offset int no Offset per paginazione (default 0)
order_by string no Colonna di ordinamento: last_name, soggetto_cognome, username, is_super_admin, ruolo_applicativo, is_active, unita_organizzativa_nome, override_count, valido_dal, valido_al (NULL = senza scadenza, ordinata come infinito). Senza order_by: soggetto_cognome, poi username, ASC. Fuori whitelist → 400 E_VALIDATION_INPUT (dal 2026-10-20)
order_dir string no ASC o DESC (altro valore: 400). Senza order_dir le colonne data (valido_dal, valido_al) partono DESC, le altre ASC

1.2 POST /api/v1/amm-software/operatori/ -- Crea utente¶

Crea un nuovo operatore completo: credenziale, soggetto persona fisica, risorsa umana e veste OPERATORE. La creazione e' orchestrata dalla funzione DB anagrafiche.fn_crea_operatore_v2.

Contract Fase 1 multi-face: il payload accetta is_super_admin (booleano). Il campo legacy ruolo_sistema e' rifiutato con E_AMM_VALIDAZIONE.

Payload JSON:

Campo Tipo Obbligatorio Descrizione
cognome string si* Cognome operatore (*solo se soggetto_id non valorizzato)
nome string si* Nome operatore (*solo se soggetto_id non valorizzato)
codice_fiscale string si* Codice fiscale italiano (*solo se soggetto_id non valorizzato)
username string si Username per login
email string si Email operatore
qualifica_id int si ID qualifica (da lookup)
is_super_admin bool no true per binding profilo SUPER_ADMIN, default false
soggetto_id UUID no Se valorizzato: associa soggetto esistente (flusso B). Se assente: crea soggetto PF nuovo (flusso A)
unita_organizzativa_id int no ID unita' organizzativa di appartenenza
data_nascita string no Data nascita (formato YYYY-MM-DD)
sesso string no* M, F o X. Nessun default (2026-10-09): nel flusso A il soggetto nuovo e' un privato, e senza sesso il guard del DB rifiuta con E_SESSO_OBBLIGATORIO (campo sesso), prima del consenso al riuso. Nel flusso B non si legge
valido_dal string no Data inizio validita' (default data corrente)
valido_al string no Data fine validita'
comune_nascita_id int no ID comune di nascita
indirizzo_resid_dettaglio_id int no ID dettaglio indirizzo residenza
indirizzo_domfisc_dettaglio_id int no ID dettaglio indirizzo domicilio fiscale
riusa_auth_user_id int no Il consenso al riuso: l'id della credenziale gia' esistente per l'email, che l'admin ha visto e confermato (vedi sotto). Al primo tentativo non si manda

Note sul contract:

  • Niente ruolo_sistema: il payload con la chiave legacy viene rifiutato prima di chiamare il repo. La promotion ad ADMIN passa da is_super_admin: true.
  • Niente password: la sceglie la persona attivando l'invito (regola unica dell'invito). Niente attivo: la veste OPERATORE nasce spenta e la accende l'attivazione dell'invito.
  • Email gia' di una credenziale (una persona, una credenziale): la credenziale si riusa, con username e password suoi; la risposta lo dice (credenziale_riusata, username effettivo). Il riuso vuole il consenso, in due tempi:
  • il primo tentativo, senza riusa_auth_user_id, risponde 409 E_CREDENZIALE_DA_CONFERMARE con ui_action = confirm_and_retry;
  • il pannello legge la credenziale (§1.2-bis), la mostra all'admin e, se conferma, ripete con riusa_auth_user_id = l'id letto. Se nel frattempo la credenziale e' cambiata, il DB chiede di nuovo.

Se l'email e' di una credenziale di un'altra persona fisica la risposta e' 400 E_CREDENZIALE_ALTRA_PERSONA (campo email): non si conferma, si corregge l'email. - Niente ruolo_applicativo: per il drawer admin-software e' implicitamente OPERATORE. Le vesti CLIENTE_PORTALE, FORNITORE_PORTALE, SHOP_CUSTOMER nascono da flussi di invito dedicati (vedi api_invito_portale_shop.md).

Risposta: dettaglio utente creato (stesso formato di GET dettaglio §1.3), piu' credenziale_riusata.

Esempio curl:

curl -X POST -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{
    "cognome": "Rossi",
    "nome": "Mario",
    "codice_fiscale": "RSSMRA85M01H501Z",
    "username": "mrossi",
    "email": "m.rossi@example.com",
    "qualifica_id": 1,
    "is_super_admin": false,
    "unita_organizzativa_id": 2
  }' \
  "https://host/api/v1/amm-software/operatori/"

1.2-bis GET /api/v1/amm-software/operatori/credenziale-per-email/ -- Credenziale di un'email¶

I dati del dialog di conferma del riuso (§1.2): la credenziale che porta l'email, con username e vesti. Legge script.fn_get_credenziale_per_email, la stessa lettura con cui la madre compone il rifiuto E_CREDENZIALE_DA_CONFERMARE: dialog e rifiuto dicono la stessa cosa. Solo SUPER_ADMIN (AdminAPIView; a DB nessun guard, decisione di Tid del 2026-09-27).

Parametro Tipo Obbligatorio Descrizione
email string no L'email del modulo di creazione. Maiuscole e spazi non contano; assente o vuota = nessuna credenziale

Risposta: data.credenziale = {auth_user_id, username, vesti} oppure null se l'email non ha credenziale (anche vuota o assente: nessun 400). vesti e' in ordine di id, ogni voce {ruolo_applicativo, attivo, soggetto}; lista vuota se la credenziale non ha vesti. Due credenziali con la stessa email → 500 E_CREDENZIALE_EMAIL_AMBIGUA.

{"data": {"credenziale": {"auth_user_id": 42, "username": "mario.rossi",
  "vesti": [{"ruolo_applicativo": "CLIENTE_PORTALE", "attivo": true, "soggetto": "Rossi Srl"}]}}}

1.4 PATCH /api/v1/amm-software/operatori/{id}/ -- Aggiorna utente¶

Aggiorna i campi modificabili di un utente. Solo i campi presenti nel payload vengono modificati. Dopo la modifica, la cache permessi dell'utente viene invalidata.

Fino a quel giorno l'interruttore lasciava valido_al com'era. Sulla veste: solo attivo, il tipo resta (R-DB-1, 2026-10-02 — prima lo spegnimento scriveva DISABILITATO, e la tabella oggi lo rifiuta con E_RUOLO_APPLICATIVO_RITIRATO). ⛔ Non la riaccende (D-3, 2026-10-04): una veste spenta si riattiva col reinvio dell'invito (§«Invito operatore»), e la accende la persona attivando il link.
  • is_super_admin lega o slega il profilo SUPER_ADMIN sulla stessa veste
  • payload senza is_super_admin ne' attivo → nessuno dei due tocchi

Parametri path: id (int) -- auth_user_id dell'utente.

  • Una chiave fuori dalla tabella sopra e un corpo senza campi → 400 E_AMM_VALIDAZIONE (dal 2026-10-20: prima la chiave si scartava e il corpo vuoto rispondeva 200 senza scrivere).

1.5 POST /api/v1/amm-software/operatori/{id}/disabilita/ -- Disabilita utente¶

Disabilita un utente: la veste OPERATORE di riferimento attivo=false (il tipo resta, R-DB-1), la sua risorsa umana attivo=false+valido_al=oggi. Sincronizza auth_user.is_active, invalida la cache permessi a commit avvenuto, invalida gli inviti operatore pendenti di quella veste (A-5, 2026-10-02: prima un invito in volo poteva ancora riaccenderla) e mette in blacklist le sessioni della sola veste operatore (refresh JWT col claim identita_id di quella veste), nella stessa transazione: una chiusura fallita annulla anche la disabilitazione. Le sessioni delle altre vesti della credenziale (shop, portale) restano aperte (D-5, 2026-10-02 — prima si chiudevano tutte).

Parametri path: id (int) -- auth_user_id dell'utente.

Payload: nessuno.

Guard "ultimo super admin": il preview lato Python legge can_disable dal detail (Fase 1) ed evita il round-trip se l'utente e' l'unico SA attivo (short-circuit con E_PROFILO_ULTIMO_SUPER_ADMIN). In caso di race tra sessioni, il trigger DB trgfn_profili_accesso_bindings_guard_ultimo_super_admin e' l'autorita' finale: il service traduce il DatabaseError in ServiceError(E_PROFILO_ULTIMO_SUPER_ADMIN) preservando il code per l'envelope errore (HTTP 409).

Regole:

  • Ordine disattivazione: figlio (identita_digitali) prima del padre (risorse_umane) per rispettare il framework ATTIVO del DB.
  • Chiama anagrafiche.fn_sync_auth_user_is_active per sincronizzare auth_user.is_active.
  • Invalida la cache permessi dell'utente (a commit avvenuto).
  • Blacklist dei refresh JWT della sola veste operatore; una chiusura fallita annulla anche la disabilitazione.

✅ Chiuso M-5 (2026-10-02): si spegne la sola veste operatore e si chiudono le sole sue sessioni; le vesti portale e shop della stessa credenziale restano come sono, connesse.

Risposta: dettaglio utente aggiornato (con attivo=false, veste_attiva=false, ruolo_applicativo="OPERATORE"; is_active resta true se la credenziale ha un'altra veste accesa).

Esempio curl:

curl -X POST -H "Authorization: Bearer <token>" \
  "https://host/api/v1/amm-software/operatori/1/disabilita/"

1.6 ~~POST /api/v1/amm-software/operatori/{id}/riattiva/~~ -- Ritirato (D-3)¶

⛔ Ritirato il 2026-10-04 (decisione D-3 di Tid, piano accessi L-5): la rotta non esiste più, e nemmeno la riattivazione via PATCH attivo: true (§1.4). Un operatore spento si riattiva col reinvio dell'invito (POST operatori/{id}/reinvia-invito/, api_invito_operatore.md):

  • il gesto dell'amministratore riapre la risorsa umana (il rapporto: attivo=true, valido_al=NULL, valido_dal intatto) nella transazione dell'emissione del token;
  • la veste (la porta) resta spenta finché la persona non attiva il link; chi ha già una password lo fa con un clic (token CROSS).

Il perché: nessuna veste torna attiva senza che la persona lo sappia. L'endpoint ritirato riscriveva anche valido_dal = oggi, perdendo l'inizio del rapporto. Il binding SUPER_ADMIN, come prima, non si ripristina da sé.

⛔ Tutte le rotte operatori/{id}/… valgono per le sole credenziali di categoria OPERATORE (dal 2026-10-02): un cliente del portale o l'utente tecnico di un processo rispondono E_AMM_OPERATORE_NOT_FOUND (404) come un id inesistente. Senza, i comandi spegnerebbero la veste OPERATORE di una macchina — la sua veste e' OPERATORE con tecnica, e fermarla e' affare del pannello dei processi (A-6).

La regola vale anche per override-aree/, override-azioni/ e override-oggetti/, in GET e PUT (2026-10-20: prima un id non operatore riceveva una lista vuota, o gli override in scrittura).

2.7 GET /api/v1/amm-software/operatori/{id}/permessi-ereditati/ -- Livelli ereditati dal profilo¶

⭐ A cosa serve. Alimenta la colonna «ereditato» del pannello permessi. 1 AD_HOC l'identita' digitale dell'utente
2 REPARTO l'unita' organizzativa
3 PORTALE il ruolo applicativo dell'identita'

Per un utente con un binding AD_HOC la lettura per reparto darebbe un valore plausibile e sbagliato, su una schermata di sicurezza.         "area_id": 2,
        "area_codice": "vendite",
        "area_descrizione": "Vendite",
        "livello": "LETTURA",
        "profilo_nome": "Profilo reparto Amministrazione",
        "profilo_tipo": "REPARTO"

    "azioni": [
      {
        "azione_id": 3,

6.1 GET /api/v1/amm-software/processi/presidi/¶

Lo stato di tutte le viste-presidio del cantiere «nessun processo senza operatore», in un round-trip: per ognuna il conteggio, le prime righe e la descrizione.

⭐ La natura di ogni presidio la dichiara il DATABASE, non il backend. È il COMMENT della vista a dire se «deve restare VUOTA» oppure se è «un registro di DEBITO che deve CALARE», e il backend lo consegna in descrizione leggendolo con obj_description. ⛔ Un elenco di eccezioni scritto nel backend o nel frontend sarebbe la seconda sede della stessa decisione, e la seconda diverge.

⛔ Quante siano non è scritto da nessuna parte, ed è una scelta. Dal 2026-09-10 l'elenco è il catalogo dbops.presidi (natura ZERO), letto da PresidiRepository.stato_presidi; fino a quel giorno era la costante PRESIDI_PROCESSI di processi_repository.py, oggi rimossa. Il nome della vista esce qualificato collo schema (ci sono viste di dbops e di maintenance). Un numero copiato accanto a un elenco che cresce invecchia in silenzio: fino al 2026-09-07 il docstring della view diceva «i SEI presidi» e alla stessa data l'elenco ne contava dieci.

Response shape: presidi è una lista; con_righe è il numero che si guarda per primo.

Campo Significato

descrizione il COMMENT della vista — è lì che sta la differenza fra «deve essere zero» e «deve calare»
significato, azione il testo per chi agisce (dbops.presidi_testi, la riga senza variante), nella lingua di chi legge con ripiego su it. null se il presidio non ha testo: il pannello ripiega sulla descrizione

6.1-bis GET /api/v1/amm-software/processi/presidi/conteggi/ — la testata sola, per il pallino¶

Scopo. I tre numeri della testata — totale, con_righe, non_letti — senza le prime righe. È la sorgente del pallino dei presidi in topbar (decisione #8 di Tid, 2026-09-18; piano piano-be-fe-osservabilita-pallino-e-superfici.md §2): un contatore ambientale letto ogni cinque minuti da ogni scheda aperta, che non deve pagare le righe di esempio.

Contesto. Stesso giro di §6.1 (PresidiRepository.stato_presidi(con_righe=False): stesse viste ZERO dal catalogo, stesso fn_conta_presidio, stesso isolamento per presidio), stessa porta (AdminAPIView). ⛔ È un parametro del repository e non un secondo metodo: una copia «senza righe» divergerebbe dalla prima al primo campo nuovo, e il pallino direbbe una cosa e il pannello un'altra. Il pannello, quando ricarica, passa i suoi numeri al pallino (usePresidiPolling osserva lo store): le due letture non possono raccontare due stati.

Input. Nessuno.

Output.

{ "data": { "totale": 20, "con_righe": 1, "non_letti": 0 } }
Campo Significato
totale quanti presidi ZERO sono stati guardati (compresi i non letti)
con_righe quanti hanno righe: il numero rosso del pallino
non_letti quanti non si sono potuti leggere: il numero giallo — cecità, non guasto, e non si somma agli accesi

Regole. Un presidio che non si legge non è un errore di questa risposta: è non_letti + 1, per contratto. Chi non passa la porta riceve 403 e il pallino non compare (il composable si spegne definitivamente su 403/401, come il badge delle code per chi non ha l'area core). ⚠️ La rotta sta sotto processi/, prima di <str:codice>/ — stessa regola d'ordine di presidi/; il test test_processi_presidi_conteggi_api.py pinna che risolva a questa view e non al dettaglio di un processo chiamato «presidi».

Dipendenze DB. dbops.presidi (catalogo), dbops.fn_conta_presidio (SECURITY DEFINER, attraversa la RLS).

6.2 POST /api/v1/amm-software/processi/{codice}/esegui-ora/ — «Esegui ora» su una sveglia¶

Accoda un lavoro ESEGUI_PROCESSO su dbops.coda_lavori per la sveglia di deploy indicata, con lo scope di chi preme (run_as = OPERATORE); il drenatore (draina_coda_lavori, ogni minuto) lancia bin/run-command.sh <comando> come sottoprocesso — la stessa riga del timer, meno l'orario — e il comando registra il suo run sotto il proprio processo con origine = COMMAND e l'utente di chi ha premuto. Il web non esegue niente. Brief: work-done/brief-db-avvio-manuale-di-un-processo.md; piano piano-be-fe-avvio-manuale-di-un-processo.md.

⚠️ Porta: AdminAPIView (v1 solo SUPER_ADMIN, decisione di Tid del 14-09). L'azione processo_avvia e' a catalogo ma non e' dichiarata sulla view — AdminAPIView non la leggerebbe, e un attributo che sembra un cancello e non lo e' sarebbe peggio di nessun attributo.

Header obbligatorio: Idempotency-Key (400 senza). E' la chiave HTTP del doppio submit; quella di business («una per unit sui lavori vivi», esegui:<unit>) la scrive il backend, ed e' quella che fa dire «gia' in coda».

Request body:

{ "unit": "zeroerp-digest-presidi-giornaliero" }

⛔ Si manda la unit, mai un comando: l'argv si risolve dal dichiarato di deploy (backend/deploy/sveglie.json), che e' la whitelist.

{ "data": { "job_id": 4321, "stato": "PENDING", "unit": "zeroerp-digest-presidi-giornaliero" } }

Rifiuti, nell'ordine in cui si valutano — tutti PRIMA di accodare:

Status Codice Quando

6.5 POST /api/v1/amm-software/processi/{codice}/identita/riattiva/ — Riattiva l'utente tecnico¶

Riaccende l'utente tecnico spento del processo per un emittente — tutta la terna: utente Django, identita' digitale, legame nel registro (script.fn_riattiva_utente_tecnico). Endpoint separato dalla creazione (POST processi/{codice}/identita/): ci si arriva dal rifiuto E_UTENTE_TECNICO_DA_RIATTIVARE di quella.

  • Header obbligatorio: Idempotency-Key.
  • Corpo: { "emittente_codice": "..." } (obbligatorio, con il codice processo del path; mancante → 400 E_CORE_VALIDATION).
  • Risposta (200): { "data": { "auth_user_id": 123 } }.
  • Errori: i guard della funzione DB, coi loro codici a catalogo; un errore DB non riconosciuto → 400 E_CORE_VALIDATION.
  • Permesso: AdminAPIView.

7. Stato del setup¶

7.1 GET /api/v1/amm-software/setup-status/¶

I contatori del banner «operatori non assegnati», in un jsonb solo da script.fn_get_setup_status(). Nessun parametro. Porta AdminAPIView.

{ "data": { "emittenti_attivi": 2, "operatori_totali": 14, "operatori_assegnati": 11,
            "operatori_admin_globali": 2, "operatori_non_assegnati": 1 } }

Un operatore conta se la sua veste e' utilizzabile oggi (script.fn_veste_utilizzabile); admin = script.fn_is_super_admin.

Regole trasversali¶

  • Autenticazione: tutti gli endpoint richiedono JWT Bearer token con binding SUPER_ADMIN (AdminAPIView)
  • Cache permessi: ogni PUT su permessi (override aree, azioni, oggetti, emittenti scope, profilo reparto) invalida la cache permessi dell'utente o del reparto interessato
  • Semantica replace: le PUT su permessi cancellano tutti i record esistenti e inseriscono i nuovi (non e' un merge/patch)
  • Ordinamento lista utenti: whitelist di §1.1 (last_name, soggetto_cognome, username, is_super_admin, ruolo_applicativo, is_active, unita_organizzativa_nome, override_count, valido_dal, valido_al); una colonna fuori whitelist ripiega sull'ordine di default, un order_dir estraneo e' un 400
  • Throttling: l'endpoint lista utenti ha throttling search attivo
