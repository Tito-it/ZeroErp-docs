API Listini (Vendite)¶

Scopo¶

Esporre via HTTP la gestione completa dei listini vendite: anagrafica listino, versioni temporali e righe prezzo.

⚠️ Rimossi da F2-BE-13 (verificato sul codice il 2026-08-19): le rotte /associazioni/ e /test-prezzo/, e con loro i campi associazioni_count e associazioni nei payload. Nel modello v5 il listino si sceglie dalla matrice categorie_clienti_listini o dal contratto, non da una tabella di associazione dedicata. Le sezioni relative restano qui come lapidi (§5, §6): dicono cosa e' sparito e cosa usare al suo posto, perche' una pagina che descrive un endpoint inesistente e' indistinguibile da una che ne descrive uno vivo.

Contesto¶

Tutti gli endpoint risiedono sotto /api/v1/vendite/listini/ e sono implementati in: - apps/vendite/api/views_listini.py - apps/vendite/services/listini_service.py - apps/vendite/db/listini_repository.py

Il backend segue il modello DB-first del progetto: - PostgreSQL resta source of truth per vincoli, overlap temporali, unicita` e resolver prezzo; - Django orchestra parsing HTTP, validazione applicativa minima, envelope risposta e traduzione errori.

Le API richiedono JWT (Authorization: Bearer <token>) e usano l'envelope standard:

{
  "data": {},
  "meta": {
    "request_id": "..."
  }
}

Base URL¶

/api/v1/vendite/listini/

1. Lista e creazione listini¶

1.1 Lista listini¶
Metodo GET
URL /api/v1/vendite/listini/

Query param¶

Parametro Tipo Obbligatorio Descrizione
search string No Ricerca libera: le colonne le decide il catalogo della lista vendite.listini (ricerca_full nella configurazione). Sotto 3 caratteri il termine si ignora (nessun 400)
utility_id int No Filtro per utility (FK config.utilities)
tipologia_id int No Filtro per tipologia listino (FK config.listini_tipologie)
attivo bool No Filtro attivo/disattivo; parsing rigoroso
in_scadenza bool No true = solo i listini con la versione in vigore in scadenza senza successore, false = gli altri; parsing rigoroso. La regola è del DB (§7). È il filtro del badge delle scadenze
limit int No Righe per pagina, default 25, max 200; fuori da 1..200 → 400 E_VALIDATION_INPUT
offset int No Scostamento, default 0 (negativo → 400); la page della risposta si ricava da qui
order_by string No codice (default), descrizione, utility_descrizione, tipologia_descrizione, attivo, data_insert, data_update, giorni_alla_scadenza
order_dir string No asc oppure desc

utility_id e tipologia_id: stringa vuota equivale a parametro assente; non numerici → 400 E_VALIDATION_INPUT, ≤ 0 → 400 E_VENDITE_VALIDATION. Permesso modello ("vendite", "listino") su tutte le rotte di questa pagina. ⚠️ La paginazione è limit/offset: page/page_size sono un 400 E_VALIDATION_INPUT (dal 2026-10-20; prima erano ignorati).

Risposta (200)¶

{
  "data": {
    "count": 1,
    "page": 1,
    "page_size": 25,
    "total_pages": 1,
    "results": [
      {
        "id": 10,
        "codice": "LIST-GAS-2026",
        "descrizione": "Tariffe consumo gas 2026",
        "utility_id": 1,
        "utility_codice": "GAS",
        "utility_descrizione": "Gas",
        "tipologia_id": 1,
        "tipologia_codice": "CONSUMO",
        "tipologia_descrizione": "Consumi",
        "attivo": true,
        "versioni_count": 2,
        "giorni_alla_scadenza": null
      }
    ]
  }
}

1.2 Crea listino¶
Metodo POST
URL /api/v1/vendite/listini/

Body JSON¶

Campo Tipo Obbligatorio Descrizione
codice string Si Codice univoco listino (immutabile dopo create)
descrizione string Si Descrizione listino
utility_id int Si FK config.utilities — intero positivo (per il commercio usare la utility Base, id=5 nel seed standard)
tipologia_id int Si FK config.listini_tipologie — intero positivo; la coppia (utility_id, tipologia_id) deve esistere attiva in config.listini_tipologie_utilities (guard DB)
emittente_soggetto_ruolo_id int Si L'emittente fiscale (soggetto-ruolo) a cui il listino appartiene — intero positivo
meta object No Metadati liberi
attivo bool No Default DB true

Risposta (200)¶

Restituisce il dettaglio completo del listino creato, con l'array versioni. Una chiave fuori dall'elenco del body → 400 E_VENDITE_VALIDATION.

Errori tipici¶

  • 400 E_VENDITE_VALIDATION:
  • utility_id, tipologia_id o emittente_soggetto_ruolo_id mancanti, nulli, non numerici, non positivi
  • chiave fuori elenco
  • Combinazione (utility_id, tipologia_id) non ammessa dalla matrice config.listini_tipologie_utilities
  • payload JSON non coerente
  • 400 E_VENDITE_FK: utility_id / tipologia_id non esistenti (FK violation)
  • 409 E_VENDITE_DUPLICATO: codice listino duplicato (uq_listini_codice)

2.2 Aggiorna listino¶
Metodo PATCH
URL /api/v1/vendite/listini/{listino_id}/

Body JSON¶

Campi ammessi (tutti opzionali; almeno uno deve essere presente):

Campo Tipo Nullable Descrizione
descrizione string No Nuova descrizione
utility_id int No Nuova utility (se inviato, NOT NULL; guard matrice DB)
tipologia_id int No Nuova tipologia (se inviato, NOT NULL; guard matrice DB)
emittente_soggetto_ruolo_id int No Nuovo emittente (se inviato, intero positivo, non null)
meta object Si Metadati liberi
attivo bool No Attivazione / disattivazione

Regole specifiche¶

  • codice è immutabile a livello API (trigger DB trg_listini_a10_protect_codice_upd lo conferma).
  • utility_id e tipologia_id non possono essere inviati a null: se presenti nel payload devono essere interi positivi. Il cambio coppia è validato dal trigger DB trg_listini_a10_guard_tipologia_utility_ins_upd contro la matrice config.listini_tipologie_utilities.
  • La PATCH legge il corpo con corpo_oggetto (corpo non oggetto → 400 E_VALIDATION_INPUT); una chiave fuori elenco → 400 E_VENDITE_VALIDATION.
  • Se nessun campo supportato è presente nel payload, restituisce 400 E_VENDITE_VALIDATION.

Errori tipici¶

  • 404 E_VENDITE_LISTINO_NOT_FOUND
  • 400 E_VENDITE_VALIDATION:
  • tipologia_id inviato come null
  • Combinazione (utility_id, tipologia_id) non ammessa dalla matrice
  • Payload vuoto

1.5 Elimina listino mai usato¶
Metodo DELETE
URL /api/v1/vendite/listini/{listino_id}/

Elimina un listino solo se non ha versioni: versioni_count == 0. Caso d'uso tipico: listini di test creati per errore. Per disattivare un listino con figli, usare PATCH attivo=false.

⚠️ Il secondo controllo storico — associazioni_count == 0 — non esiste piu' da F2-BE-13 (listini_service.fn_delete_listino).

Risposta (200):

{ "data": { "deleted": true, "id": 10 } }

Errori tipici:

  • 400 E_VENDITE_VALIDATION se il listino ha versioni
  • 404 E_VENDITE_LISTINO_NOT_FOUND

2bis. Tipologie ammesse per utility¶

Endpoint di supporto per il frontend: dato un utility_id, restituisce le tipologie di listino ammesse dalla matrice config.listini_tipologie_utilities (solo righe attive). Usato dal ListinoDrawer per popolare il Select tipologia al cambio utility.

2bis.1 Lista tipologie per utility¶
Metodo GET
URL /api/v1/vendite/listini/tipologie-per-utility/

Query param¶

Parametro Tipo Obbligatorio Descrizione
utility_id int Si FK config.utilities, intero positivo

Se utility_id manca o è stringa vuota, la risposta è 400 E_VENDITE_VALIDATION con detail che riporta esplicitamente "utility_id è obbligatorio".

Risposta (200)¶

Envelope standard con chiave results (pattern lookup dedicati):

{
  "data": {
    "results": [
      {
        "id": 1,
        "codice": "CONSUMO",
        "descrizione": "Consumi",
        "e_consumo": true,
        "e_quota_fissa": false,
        "e_imposta": false,
        "e_onere": false,
        "e_prodotto": false,
        "e_servizio": false,
        "ordinamento": 10
      },
      {
        "id": 2,
        "codice": "QUOTA_FISSA",
        "descrizione": "Quote fisse",
        "e_consumo": false,
        "e_quota_fissa": true,
        "e_imposta": false,
        "e_onere": false,
        "e_prodotto": false,
        "e_servizio": false,
        "ordinamento": 20
      }
    ]
  }
}

L'ordinamento segue ordinamento ASC, descrizione ASC. Sono restituite solo le tipologie attive (listini_tipologie.attivo = true) e solo le righe della matrice attive (listini_tipologie_utilities.attivo = true).

Errori tipici¶

  • 400 E_VENDITE_VALIDATION: utility_id mancante, vuoto o non positivo.

Note¶

  • L'utility deve esistere per ottenere righe. Per utility_id inesistente la risposta è 200 con results: [] (no 404) — accettabile per un endpoint lookup.
  • Non applica scope per emittente: config.listini_tipologie è tabella globale.

3. Versioni listino¶

3.1 Lista versioni¶
Metodo GET
URL /api/v1/vendite/listini/{listino_id}/versioni/

La pagina della lista vendite.listini_versioni (il tab «Versioni» del drawer listino): stessa busta paginata del §1.1. Per ogni versione i dati principali, righe_count e giorni_alla_scadenza (§7). Il dettaglio (§3.3) ha gli stessi campi tranne giorni_alla_scadenza. ⚠️ Fino al 2026-10-31 era la collezione completa {count, results}, senza pagina.

Parametro Tipo Obbligatorio Descrizione
search string No Ricerca libera sulle colonne che il catalogo accende (codice_versione); sotto 3 caratteri si ignora
limit · offset int No Come §1.1
order_by string No valido_dal (default, DESC), valido_al, codice_versione, righe_count, stato, giorni_alla_scadenza. Le date senza direzione si ordinano DESC
order_dir string No asc oppure desc

Campi dal modello del documento (giro 12, brief-modello-documento-vendita §16, 2026-10-28):

Campo Cosa dice
stato il codice dello stato (BOZZA, ATTIVA, CHIUSA) dal vocabolario config.stati_doc_listino_versioni: e' lo stato del DB, nessuna deduzione dalle date
azioni_permesse le action_key dei passaggi che l'operatore puo' fare dallo stato della versione (script.fn_doc_azioni_permesse, che applica l'azione della riga del passaggio). Oggi solo attiva, da BOZZA, a chi ha attiva_listino. Permesso ⇒ nascondi
attivazione_blocco_reason · attivazione_blocco_reason_key perche' «Attiva» e' spento (codice macchina e chiave i18n del primo motivo di script.fn_check_versione_listino_attivabile, la stessa con cui il verbo rifiuta), da vendite.vw_listini_versioni_azioni; null = niente lo vieta. Sono le colonne che il registro config.azioni_riga dichiara per ATTIVA_VERSIONE_LISTINO
eliminazione_blocco_reason · eliminazione_blocco_reason_key perche' «Elimina» e' spento (VERSIONE_NON_IN_BOZZA, VERSIONE_CITATA: il primo motivo di script.fn_check_versione_listino_eliminabile), dalla stessa vista; registro ELIMINA_VERSIONE_LISTINO (§16.13, 2026-10-29)
chiusura_blocco_reason · chiusura_blocco_reason_key perche' «Chiudi» e' spento (VERSIONE_NON_ATTIVA: il primo motivo di script.fn_check_versione_listino_chiudibile, senza data), dalla stessa vista; registro CHIUDI_VERSIONE_LISTINO (§16.16, 2026-10-29). «Clona» non ha colonne: si clona da qualunque stato
chiusura_programmata la versione e' ATTIVA con valido_al scritto: il job la porta a CHIUSA quando la fine passa. Fra la fine e il job resta ATTIVA, e si mostra cosi'

3.3 Dettaglio versione¶
Metodo GET
URL /api/v1/vendite/listini/{listino_id}/versioni/{ver_id}/

3.4 Aggiorna versione¶
Metodo PATCH
URL /api/v1/vendite/listini/{listino_id}/versioni/{ver_id}/

Campi modificabili per stato¶

Li decide il DB (L-5, giro 12): il guard vendite.trgfn_listini_versioni_guard_per_stato. Il backend non filtra per stato e trasporta il rifiuto.

Stato versione Campi modificabili
BOZZA codice_versione, valido_dal, valido_al, meta, attivo
ATTIVA nessun campo da qui: la fine (valido_al) solo da «Chiudi» (§3.6-bis) o dall'attivazione di una successiva
CHIUSA nessun campo (stato terminale)

Razionale: una versione ATTIVA ha giapropagato i prezzi negli snapshot dicommesse_attivita/attivita_fatturabili. Modificarecodice_versione,valido_dalometasu una versione operativa creerebbe drift tra documenti emessi e stato listino. Solo la fine resta modificabile, e solo dai verbi che la scrivono (C-4 = a, 2026-10-29): cosi' vale sempre la regola «la fine non sta nel passato». Per cambiare prezzi su un periodo gia attivo, si crea una nuova versione (clone + edit + activate).

Errori tipici¶

  • 409 E_LISTINO_VERSIONE_CAMPO_NON_MODIFICABILE (dal DB): il campo non si cambia nello stato della versione; la frase nomina il primo campo. Fino al 2026-10-28 era un 400 E_VENDITE_VALIDATION del backend
  • 500 E_LISTINO_VERSIONE_FINE_SOLO_DAL_VERBO (TECNICO, dal DB): valido_al di una ATTIVA dal PATCH. Nessuna interfaccia lo produce: si passa da §3.6-bis
  • 404 E_VENDITE_LISTINO_VERSIONE_NOT_FOUND

3.5 Clona versione¶
Metodo POST
URL /api/v1/vendite/listini/{listino_id}/versioni/{src_ver_id}/clona/

Crea una nuova versione BOZZA dello stesso listino copiando tutte le righe attive della versione sorgente, da qualunque stato (anche da una BOZZA: C-1 = a, 2026-10-29). La copia e' il verbo vendite.fn_clona_versione_listino, in una transazione: versione, righe attive e componenti attivi dei compositi con la validita' ricalcolata sul periodo comune alla distinta e alla versione nuova. Workflow operativo "cambio prezzi": clona V001 in V002 BOZZA, modifica i prezzi che cambiano, attiva V002. La sorgente non viene toccata.

Body JSON¶

Campo Tipo Obbligatorio Descrizione
codice_versione string Si Codice univoco per il listino
valido_dal date Si Data inizio validita` (vedi vincolo D2 sotto)
valido_al date No Data fine validita`, NULL = aperta

La nuova versione nasce in stato BOZZA (lo stato iniziale, dal guard della nascita: il backend non lo scrive) con attivo=true e meta vuoto. Ogni altra chiave, meta e attivo compresi, → 400 E_VENDITE_VALIDATION: fino al 2026-10-29 meta e attivo si validavano e poi si ignoravano in silenzio. Le righe vengono copiate con attivo=true (le righe non attive della sorgente sono escluse).

Risposta (200)¶

Il dettaglio della versione nuova (§3.1) piu' i conteggi della copia: righe_copiate, componenti_copiati, componenti_saltati (i componenti senza giorni in comune fra la distinta e la versione nuova: non si copiano).

Vincolo D2 — valido_dal e retroattivita`¶

nuova.valido_dal puoessere retroattivo (precedente alla data odierna), ma **non puo essere inferiore a sorgente.valido_dal**. Cioprotegge da cloni "prima dell'inizio" della versione che si vuole sostituire. Lo dice il verbo (script.fn_check_versione_listino_clonabile), sul campovalido_dal`.

Il clone retroattivo non modifica le fatturazioni giaemesse nel periodo: queste continuano a basarsi sullo snapshot incommesse_attivita/attivita_fatturabili. Per correggerle e necessaria una rettifica DB-L4 (dominio separato, vedi dev/work-in-progress/sviluppo-rettifiche.md).

Errori tipici¶

  • 400 E_LISTINO_VERSIONE_CLONE_PRIMA_DELLA_SORGENTE (dal DB, campo valido_dal) se nuova.valido_dal < sorgente.valido_dal. Fino al 2026-10-29 era un 400 E_VENDITE_VALIDATION del backend
  • 400 E_VENDITE_VALIDATION se manca un campo obbligatorio
  • 409 E_VENDITE_DUPLICATO se codice_versione duplicato per il listino (uq_listini_versioni_listino_codice)
  • 404 E_VENDITE_LISTINO_VERSIONE_NOT_FOUND se la sorgente non esiste

3.6 Elimina versione¶
Metodo DELETE
URL /api/v1/vendite/listini/{listino_id}/versioni/{ver_id}/

3.6-bis Chiudi versione¶
Metodo POST
URL /api/v1/vendite/listini/{listino_id}/versioni/{ver_id}/chiusura/

«Chiudi» e «Rimuovi chiusura» di una versione ATTIVA: fissa la fine della validita' (la chiusura programmata) o la toglie. Decide il verbo vendite.fn_programma_chiusura_versione_listino (§16.14, C-2 = a, 2026-10-29). Lo stato non cambia: CHIUSA la scrive il job quando la fine passa. Nessun permesso di passaggio (non e' un passaggio di stato): il permesso d'area change, come il PATCH che sostituisce (post_accesso = "change": senza, la POST chiederebbe add).

Body JSON¶

Campo Tipo Obbligatorio Descrizione
valido_al date | null Si la nuova fine; null toglie la chiusura. ⚠️ La chiave e' obbligatoria anche quando e' null: un corpo vuoto e' un 400

Altre chiavi → 400 E_VENDITE_VALIDATION. Risposta: il dettaglio della versione (§3.1).

Errori tipici¶

  • 409 E_LISTINO_VERSIONE_NON_CHIUDIBILE: la versione non e' ATTIVA
  • 400 E_LISTINO_VERSIONE_FINE_NEL_PASSATO (campo valido_al): la fine precede oggi (la data operativa). Prima il limite stava solo nel frontend
  • 400 E_DATA_AL_MINORE_DAL: la fine precede l'inizio (guard comune delle date)
  • 409 E_VENDITE_LISTINO_VERSIONE_OVERLAP: togliere la chiusura sovrapporrebbe la versione ATTIVA successiva
  • 404 E_VENDITE_LISTINO_VERSIONE_NOT_FOUND

3.7 Cambia stato versione¶
Metodo POST
URL /api/v1/vendite/listini/{listino_id}/versioni/{ver_id}/stato/

È l'attivazione (BOZZA → ATTIVA), l'unico passaggio manuale della matrice config.transizioni_stati_listino_versioni. Decide il verbo vendite.fn_attiva_versione_listino (giro 12, L-3 e L-4, 2026-10-28).

Body JSON¶

{
  "stato": "ATTIVA",
  "dry_run": false
}
Campo Tipo Obbligatorio Descrizione
stato string Si solo ATTIVA. ATTIVA → CHIUSA e' di processo: si programma con «Chiudi» (§3.6-bis) e la scrive il job a fine scaduta
dry_run bool No Se true, non scrive nulla e restituisce l'anteprima delle versioni che verrebbero chiuse. Default false. ⚠️ Solo il booleano JSON: un altro valore (anche "true") e' un 400 sul campo

Altre chiavi → 400 E_VENDITE_VALIDATION.

Il permesso¶

La view dichiara post_passaggio = PassaggioDocumento(vendite.listini_versioni, "ver_id", campo_stato="stato"): l'azione la legge dalla riga del passaggio (attiva_listino), prima della transazione, anche per il dry_run. Senza l'azione: 403.

Che cosa fa il verbo, in una transazione¶

  1. la versione nel perimetro dell'utente, presa FOR UPDATE;
  2. la riga comune del passaggio: gia' attiva → E_DOC_GIA_NELLO_STATO; l'azione;
  3. il primo motivo che vieta (script.fn_check_versione_listino_attivabile): versione spenta, nessun prezzo;
  4. la chiusura delle precedenti (decisione D3): le versioni ATTIVE e accese dello stesso listino, con decorrenza precedente e periodo che tocca la nuova, prendono valido_al = nuova.valido_dal - 1;
  5. lo stato ATTIVA attraverso la porta.

Prima (fino al 2026-10-28) tutto questo era nel backend.

Modalitadry_run` (preview UI)¶

Con dry_run: true il verbo gira in un savepoint annullato: la chiamata rifiuta con gli stessi codici dell'attivazione vera (vedi «Errori tipici»), non lascia scritto niente e restituisce l'elenco che il verbo chiuderebbe, dallo stesso lettore del verbo (vendite.fn_versioni_listino_da_chiudere): quello che si mostra e' quello che si fa.

{
  "data": {
    "dry_run": true,
    "versione_id": 202,
    "nuovo_stato": "ATTIVA",
    "auto_close": [
      {
        "id": 101,
        "codice_versione": "V001",
        "valido_dal": "2026-01-01",
        "valido_al_prima": null,
        "valido_al_dopo": "2026-03-31"
      }
    ]
  }
}

⚠️ Fino al 2026-10-28 l'anteprima leggeva il solo lettore e non verificava i motivi: a un client senza il pulsante spento proponeva la chiusura delle precedenti per un'attivazione che il verbo avrebbe poi rifiutato.

Senza dry_run la risposta è il dettaglio della versione riletto (§3.3).

Errori tipici¶

  • 400 E_VENDITE_VALIDATION: stato diverso da ATTIVA, chiave fuori elenco, dry_run non booleano
  • 403: l'operatore non ha l'azione attiva_listino
  • 404 E_VENDITE_LISTINO_VERSIONE_NOT_FOUND: la versione non è di quel listino, o è fuori perimetro
  • 409 E_DOC_GIA_NELLO_STATO: la versione è già attiva
  • 422 E_LISTINO_VERSIONE_SPENTA, E_LISTINO_VERSIONE_SENZA_RIGHE: i motivi del verbo
  • 409 E_VENDITE_LISTINO_VERSIONE_OVERLAP se il vincolo ex_listini_versioni_no_overlap viene urtato

skipped_no_overlap (PG18, additivo): conta le righe non inserite perche' l'intersezione fra valido_dal/valido_al della versione e quelli della riga BoM e' vuota (es. richiesta una validita' antecedente alla BoM corrente del componente). Regole salva bundle¶

  • Solo versione BOZZA: il guard _assert_versione_bozza_for_riga_op rifiuta UPDATE su versioni ATTIVA/CHIUSA. Defense-in-depth col trigger DB _immutabilita_v5 (codice E_RIGA_LISTINO_VERSIONE_CHIUSA, 409).
  • Strategia tabula rasa idempotente: il repo prima soft-disattiva (attivo=FALSE) tutte le righe attive correnti per la coppia (versione, padre), poi inserisce le nuove. Garantisce stato esatto senza diff complesso. Transazione atomica.

Se l'intersezione e' vuota, la riga e' ignorata con warning + conteggio in skipped_no_overlap (evita errore SQL range lower > upper). La temporal FK fk_listrighe_comp_articoli_comp_temporal garantisce a livello DB il contenimento riga ⊆ BoM.
  • Skip prezzo null: righe con prezzo == NULL vengono ignorate (= "non gestito a bundle"; il resolver fa fallback STADIO 1 standalone). Confermare con tutti i prezzi NULL = svuotare il composito (= "elimina composito" lato UI).
  • iva_id opzionale: default lato DB.
  • Guard coerenza BoM PG18: validita riga ⊆ validita BoM ora enforced da temporal FK fk_listrighe_comp_articoli_comp_temporal (migration 20260514-12, sostituisce guard 6 trigger rimosso con migration 20260514-13). Validita riga ⊆ validita versione resta enforced dal trigger trgfn_listini_righe_comp_guard_coerenza_bom (guard residuo). Altri check (articolo_componente_id attivo, padre is_composito=TRUE, IVA padre = IVA figlio) restano nel trigger. Tutti producono E_LISTINO_RIGA_COMP_BOM_INCOERENTE (400).
