API Catalogo¶

Scopo¶

Esporre via HTTP il backend catalogo:

  • anagrafica articoli, con disattivazione/riattivazione come azioni dedicate e defaults di pre-compilazione del form
  • lookup articoli (consultazioni e righe di documento) e lookup UoM operative di un articolo
  • UoM operative articolo
  • distinta base: legami, lista configurabile, chiusura coi prezzi bundle
  • note di catalogo (articolo e legame di distinta)
  • anagrafica unità di misura, tipologie e conversioni UoM
  • metadata immutabilita' campi (non_editable_fields) sui detail
  • capability di riga (puo_gestire_bom, puo_eliminarsi, puo_chiudersi…) su articoli, UoM operative, legami e conversioni

Contesto¶

Gli endpoint risiedono sotto /api/v1/catalogo/ e sono implementati in: - apps/catalogo/api/views.py - apps/catalogo/api/note_views.py (note, dal BB make_note_views) - apps/catalogo/services/catalogo_service.py - apps/catalogo/db/catalogo_repository.py - apps/catalogo/db/catalogo_uom_repository.py - apps/catalogo/db/catalogo_bom_repository.py - apps/catalogo/db/note_repositories.py

Il backend segue il modello DB-first del progetto: - PostgreSQL governa vincoli, guard e coerenza strutturale; - Django orchestra parsing HTTP, validazione applicativa minima, envelope risposta e traduzione errori.

Tutte le risposte usano l'envelope standard:

{
  "data": {},
  "meta": {
    "request_id": "..."
  }
}

Base URL¶

/api/v1/catalogo/

1. Articoli¶

1.1 Lista articoli¶
Metodo GET
URL /api/v1/catalogo/articoli/

Query param¶

Parametro Tipo Obbligatorio Descrizione
search string No Ricerca libera: colonne e soglia le decide il catalogo della lista catalogo.articoli. Sotto soglia il termine non filtra (nessun 400: il 400 E_SEARCH_VALIDATION vale solo per il lookup, §2.1)
attivo bool No Filtro attivo/disattivo
is_composito bool No Filtro articoli composti
tipo_voce_id int No Filtro tipologia
gruppo_voce_id int No Filtro gruppo
listino_tipologia_id int No Filtro tipologia di listino dell'articolo
data_da date No Filtro data insert da (giorno dell'azienda: vedi sotto)
data_a date No Filtro data insert a, giorno incluso. I giorni sono giorni dell'azienda (fuso SYSTEM_FUSO_ORARIO, confini calcolati dal DB col BB predicato_giorno_operativo, dal 2026-10-09) (fino ad allora data_insert::date, il giorno della sessione e niente indice)
limit int No Righe per pagina, default 25, max 200
offset int No Righe da saltare, default 0
order_by string No codice, descrizione (default), uom_codice, attivo, data_insert, data_update
order_dir string No asc oppure desc. Assente: asc su ogni colonna, date comprese (dal 2026-11-24 nessuna colonna ha un verso di partenza proprio: la regola «le date partono desc» è ritirata)

⚠️ La paginazione è limit/offset: page/page_size in query sono un 400 E_VALIDATION_INPUT (dal 2026-10-20; prima erano ignorati). La risposta è {count, results} (api.md §Paginazione): dal 2026-11-24 non riporta più page e page_size.

Risposta (200)¶

{
  "data": {
    "count": 1,
    "results": [
      {
        "id": "019bbee2-5f6a-704f-bbd0-34ed84db252d",
        "codice": "ART-001",
        "descrizione": "Articolo demo",
        "uom_id": 1,
        "uom_codice": "PZ",
        "is_composito": false,
        "is_solo_componente": false,
        "requires_lotto": false,
        "attivo": true,
        "puo_gestire_bom": false,
        "motivo_non_gestibile_bom": "ARTICOLO_NON_COMPOSITO"
      }
    ]
  }
}
Capability BoM (Fase 6)¶

Ogni riga espone capability data-driven da vw_articoli_dettaglio:

  • puo_gestire_bom: bool — true se is_composito AND NOT is_solo_componente.
  • motivo_non_gestibile_bom: string | null — codice motivo quando puo_gestire_bom=false. Valori:
  • "ARTICOLO_SOLO_COMPONENTE" — articolo marcato come solo componente.
  • "ARTICOLO_NON_COMPOSITO" — articolo non composito.
  • null — quando puo_gestire_bom=true.

Il FE usa questi campi per disabilitare l'azione "manage-bom" e mostrare il motivo via tooltip i18n (chiavi catalogo.motivo_*).

1.2 Crea articolo¶
Metodo POST
URL /api/v1/catalogo/articoli/

Body JSON¶

Campo Tipo Obbligatorio Descrizione
codice string Si Codice univoco articolo
descrizione string Si Descrizione articolo
descrizione_breve string No Descrizione breve
uom_id int Si UoM base, intero > 0 (immutabile dopo la creazione). Mancante o non positivo: 400 E_CATALOGO_VALIDATION
tipo_voce_id int No Tipologia
gruppo_voce_id int No Gruppo
spesa_id int No Spesa
iva_id int No IVA
conto_contabile_vendita_id int No Conto vendita
conto_contabile_acquisto_id int No Conto acquisto
is_composito bool No Articolo composto
is_solo_componente bool No Usabile solo come componente
requires_serial bool No Richiede seriale
requires_lotto bool No L'articolo si movimenta per lotti. Fuori dal lock BoM: resta modificabile in PATCH
listino_tipologia_id int No Tipologia di listino
natura_vendita_id int No Natura di vendita (FK config.nature_vendita): decide l'instradamento post-accettazione del modello split (ORDINE/COMMESSA/CONTRATTO). Se omesso → default DB MERCE. Mai null esplicito (colonna NOT NULL): risponde E_CATALOGO_VALIDATION
modo_approvvigionamento_id int No Da dove arriva l'articolo (FK config.modi_approvvigionamento: ACQUISTO / PRODUZIONE / STOCK / NON_APPLICABILE — 2026-09-14, Blocco B di brief-db-modifiche-certe-ciclo-vendita-e-articolo). Dimensione ortogonale alla natura di vendita (dice dove va la riga, non da dove viene). Se omesso → default DB ACQUISTO. Mai null esplicito (NOT NULL): E_CATALOGO_VALIDATION col campo. Lookup: GET /core/lookup/codici/?rel=config.modi_approvvigionamento
gestito_a_magazzino bool No L'articolo movimenta giacenza. Default DB false (fail-safe: nessun articolo comincia a movimentare per distrazione). ⚠️ Non si deriva da natura MERCE: una merce può essere venduta senza passare da giacenza
lead_time_giorni int No Giorni fra richiesta e disponibilità. Nullable per modello: per una prestazione non significa niente, e 0 non è «non si applica». Negativo → E_CATALOGO_VALIDATION col campo (anticipa il CHECK)
obsoleto_dal date No Il ritiro dell'articolo: la data da cui non si sceglie più per una riga nuova (YYYY-MM-DD). Nullable: null = si sceglie; una data futura è un ritiro programmato; null in PATCH toglie il ritiro. I documenti già fatti non cambiano. Una data scritta male → E_CATALOGO_VALIDATION col campo
causale_onere_id int No La causale dell'articolo-onere (FK config.causali_onere, 2026-11-12, brief-db-addebito-trasporto-ordine §9.10): null = merce, un id fa dell'articolo un onere. Il legame è 1:1: una causale già di un altro articolo → 400 E_ARTICOLO_CAUSALE_ONERE_GIA_USATA sul campo (anche dall'indice uq_articoli_causale_onere, su due scritture concorrenti). Su un onere valgono E_ARTICOLO_ONERE_NATURA_MERCE e E_ARTICOLO_ONERE_STRUTTURA. In PATCH si cambia finché l'articolo non è usato (A-10, non_editable_fields). Le causali libere: GET /core/lookup/codici/?rel=catalogo.vw_causali_onere_assegnabili
meta object No Metadati liberi

Una chiave fuori da questo elenco è rifiutata con 400 E_CATALOGO_VALIDATION: anche voce_utility, che non esiste più (né come campo né come filtro, né in risposta). I booleani si mandano come booleani JSON.

1.3 Dettaglio articolo¶
Metodo GET
URL /api/v1/catalogo/articoli/{articolo_id}/

Output specifico¶

Il dettaglio articolo include gli array correlati e i metadata di immutabilita' (Fase 5):

  • uom_operative — array UoM operative dell'articolo, ogni riga arricchita da capability di riga (Fase 6, vedi §3.1).
  • componenti — array componenti BoM (popolato solo se is_composito=true)
  • ⛔ niente note: ritirato il 2026-11-11 (era una terza lettura delle note, senza lettori). Le note dell'articolo si leggono dalla loro lista (/api/v1/catalogo/articoli/{articolo_id}/note/, §5).
  • non_editable_fields: string[] — Fase 5: chiavi del payload non modificabili in PATCH (es. ["codice", "uom_id"]). Il FE le usa per pilotare i :disabled invece di cablare regole.
  • puo_gestire_bom: bool, motivo_non_gestibile_bom: string | null — Fase 6: capability di gestione BoM (vedi §1.1).
  • Natura di vendita (2026-06-10, da vw_articoli_dettaglio): natura_vendita_id, natura_vendita_codice_interno, natura_vendita_descrizione, natura_vendita_destinazione_tipo (ORDINE_VENDITA / COMMESSA / CONTRATTO: codici di config.sorgenti, FK dal 2026-10-19, brief-db-grammatica-unica-documenti lotto 2b). Il FE inizializza il Select "Natura di vendita" del drawer da natura_vendita_id; gli stessi campi sono disponibili anche nelle righe della lista (§1.1).
  • Approvvigionamento (2026-09-14, da vw_articoli_dettaglio): modo_approvvigionamento_id, modo_approvvigionamento_codice_interno, modo_approvvigionamento_descrizione (⛔ non _codice: il valore viene dalla colonna immutabile, linee-guida-sql §6c), gestito_a_magazzino, lead_time_giorni. ⚠️ ARTICOLI_DETAIL_COLUMNS è una proiezione per nome: una colonna nuova della vista non esce finché nessuno la nomina — le tre colonne della lista 26 (ui.lista_colonna 747-749) sono nate attivo = f e accese nello stesso commit di questa proiezione.
  • Ritiro (2026-11-11, da vw_articoli_dettaglio): obsoleto_dal, la data scritta dall'operatore, ed e_obsoleto, vero quando l'articolo è ritirato alla data operativa (script.fn_e_obsoleto, lo stesso predicato del guard di riga e del picker di riga). ⛔ Il FE legge e_obsoleto e non confronta date. Gli stessi due campi sono nelle righe della lista (§1.1).
  • Onere (2026-11-12, da vw_articoli_dettaglio): e_onere, causale_onere_id, causale_onere_codice_interno (per la logica) e causale_onere_descrizione (a video), null sulla merce. ⛔ Non _codice: il valore viene dalla colonna immutabile (linee-guida-sql §6c).

1.4 Aggiorna articolo¶
Metodo PATCH
URL /api/v1/catalogo/articoli/{articolo_id}/

Regole specifiche¶

  • codice e uom_id sono immutabili a livello API (vedi non_editable_fields nel detail).
  • natura_vendita_id e' mutabile (decisione 2026-06-10, opzione A): cambiarla vale solo per le righe documento future — le righe esistenti hanno lo snapshot di natura preso all'inserimento riga. Mai null esplicito (NOT NULL a DB): E_CATALOGO_VALIDATION.
  • attivo non e' modificabile via PATCH (Fase 7): risponde E_CATALOGO_VALIDATION con detail "usa gli endpoint /disattiva/ o /riattiva/". La transizione di stato passa solo dagli endpoint dedicati (§1.5 e §1.6).
  • L'endpoint aggiorna solo i campi presenti nel payload.
  • In assenza di campi supportati, restituisce 400.
  • ⭐ L'IVA di un kit e dei suoi componenti deve coincidere sui legami attivi da oggi in poi (E_BOM_IVA_DISCORDANTE, 400, campo iva_id). Dal 2026-11-10 la regola si giudica a fine transazione: il guard catalogo.trgfn_articoli_guard_iva_bom_attiva è un vincolo differito (D4 e D21 di brief-db-revisione-catalogo). Il PATCH apre una transazione sua, e il rifiuto arriva al suo COMMIT, fuori dal punto in cui il service traduce gli errori d'integrità: lo traduce il traduttore generale, con lo stesso codice e lo stesso campo. Prova: apps/catalogo/tests/db/test_errori_articolo_giro3_db.py.

1.5 Disattiva articolo¶
Metodo POST
URL /api/v1/catalogo/articoli/{articolo_id}/disattiva/

Regole specifiche¶

  • Soft delete logico (attivo=false)
  • Idempotente se l'articolo e' gia' inattivo
  • ⛔ Un articolo nominato da altre righe non si spegne, si ritira (Q35 (c), Tid 2026-11-12, brief-db-revisione-catalogo §16.6.7). Il trigger trgfn_prevent_deactivate_if_children, sulle tabelle col ritiro (obsoleto_dal), rifiuta con 409 E_ATTIVO_BLOCK_SI_RITIRA e fields: ["obsoleto_dal"]: la strada e' il PATCH dell'articolo con obsoleto_dal (oggi, o un giorno futuro per un ritiro programmato). Vale per le distinte (anche i legami chiusi), i documenti, i listini. I due rami E_ATTIVO_BLOCK_CHILDREN_ACTIVE / _EXIST restano per le tabelle senza ritiro. Il drawer articolo colora il campo «Ritirato dal» e ci porta l'operatore. Prova: smoke-test-catalogo-phase3.sh passo 17.

1.6 Riattiva articolo (Fase 7)¶
Metodo POST
URL /api/v1/catalogo/articoli/{articolo_id}/riattiva/

Regole specifiche¶

  • Imposta attivo=true chiamando catalogo.fn_riattiva_articolo(uuid).
  • Idempotente se l'articolo e' gia' attivo (no-op DB, ritorna dettaglio).
  • E_CATALOGO_ARTICOLO_NOT_FOUND (404) se l'id non esiste (pre-flight uniforme con il resto del dominio).
  • Pattern "padre prima, figli poi": non tocca i figli (UoM operative, righe BoM dove l'articolo e' componente, ecc.) — l'admin li riattiva esplicitamente in azioni successive.
  • Eventuali blocchi del trigger trgfn_child_requires_active_parent (parent inattivo: iva/gruppo/tipologia) si propagano come E_PARENT_*.

1.6-bis Correzione di struttura (amministratore)¶

Non ha un endpoint suo: viaggia nel PATCH dell'articolo (§1.4), nella chiave correzione_struttura.
Metodo PATCH
URL /api/v1/catalogo/articoli/{articolo_id}/
Permesso solo SUPER_ADMIN: lo giudica il verbo DB

Un articolo usato (in un documento, un listino, una commessa o in magazzino) non cambia la sua struttura (E_ARTICOLO_USATO_STRUTTURA_IMMUTABILE). La via normale è un articolo nuovo. Per un errore di caricamento l'amministratore la corregge (A-10 di brief-db-articoli-ammessi-per-documento).

Body: i campi di sempre più "correzione_struttura": {"natura_vendita_id": 3}, le sole colonne strutturali da cambiare. Quali sono lo dice il dettaglio dell'articolo, struttura_correggibile (dalla sede catalogo.fn_articolo_colonne_struttura, la stessa da cui il verbo legge le colonne ammesse). Il backend chiama prima il verbo catalogo.fn_articolo_correggi_struttura, poi l'aggiornamento, in una transazione: un aggiornamento rifiutato annulla anche la correzione. correzione_struttura da sola basta (nessun altro campo richiesto). Risposta: il dettaglio aggiornato.

  • chi non è SUPER_ADMIN: E_PERMESSO_NEGATO; correzione_struttura vuota o non oggetto, o una colonna fuori dalla sede: 400 E_PARAMETRO_INVALIDO; un valore vuoto su una colonna NOT NULL, o di un tipo che la colonna non accetta: 400 E_PARAMETRO_INVALIDO col campo = la colonna e il nome leggibile nella frase (dal 2026-11-10, D19); articolo inesistente: E_ARTICOLO_NOT_FOUND; una correzione che renderebbe non valide righe di documenti ancora aperti: 409 E_ARTICOLO_STRUTTURA_RIGHE_APERTE (i documenti in dettaglio.righe) — li solleva tutti il verbo, l'unica porta (il backend non ripete nessuna di queste regole);
  • gli altri guard dell'articolo parlano lo stesso.

Fino al 2026-10-18 la correzione era POST …/articoli/{id}/struttura/, una chiamata a parte prima del PATCH: un PATCH fallito lasciava la struttura già corretta (R-BE-1). L'endpoint è ritirato.

1.7 Defaults form articolo (Fase 8)¶
Metodo GET
URL /api/v1/catalogo/articoli/form-defaults/

Centralizza il consumo dei parametri usati dal FE per pre-compilare il form di creazione articolo. Tipi gia' risolti: il FE non duplica la conversione di /core/parameters/defaults/.

Risposta (200)¶

{
  "data": {
    "default_iva_id": 42
  }
}

Regole specifiche¶

  • default_iva_id si RISOLVE dal parametro DEFAULT_IVA (config.parameters), che porta il codice_interno dell'aliquota — non il suo id. Il lookup passa da resolve_config_id_by_codice_interno su config.iva, che filtra attivo = true e matcha sulla colonna lockata.
  • ⛔ NON si fa int() sul valore del parametro, e la ragione e' che non fallirebbe. Il codice_interno dell'aliquota ordinaria e' 22, cioe' un numero: un lettore rimasto indietro otterrebbe l'id 22, che oggi in config.iva non esiste ma che il modello ammette eccome — e il giorno che esistesse sarebbe un'aliquota SBAGLIATA proposta in silenzio, su un dato che finisce sui documenti fiscali. Verificato sul DB: codice_interno = '22' da' id 16; id = 22 non esiste.
  • Se il parametro e' assente, vuoto, o punta a un codice inesistente/disattivato, ritorna null (best-effort, no raise: il form si apre e l'operatore sceglie a mano). ⚠️ Ma non muto: il ripiego scrive un logger.warning, perche' a video null e' indistinguibile da «non c'e' un default configurato» e un seed che punta a un'aliquota disattivata sparirebbe senza lasciare traccia.
  • Override per utente/gruppo/emittente fiscale applicato dal ParameterService con il context standard (superuser bypass).

📌 Il rename e' del 2026-08-31 (DEFAULT_IVA_ID → DEFAULT_IVA): e' il terzo dei quattro passi che linee-guida-sql §6b descrive per i parametri che stoccano un id invece di una chiave naturale — l'id e' soggetto a reseed, la chiave naturale e' il contratto cross-ambiente. Il valore e' validato dal registry config.parameter_fk_surrogate, quindi da quel giorno un codice IVA inesistente nel seed viene rifiutato invece di restare a marcire. ⚠️ Il comportamento a video non cambia: il form propone la stessa aliquota di prima.

4.3 Aggiorna componente — RITIRATO (2026-11-10)¶

Il PATCH di un legame non esiste più, e con lui la rotta /api/v1/catalogo/articoli/{articolo_id}/componenti/{comp_id}/ (decisione di Tid, §14.10.3 di brief-db-revisione-catalogo). La distinta è una storia: i campi di struttura sono immutabili (E_BOM_MODIFICA_VIETATA), e l'unica cosa che di un legame cambia, la fine, passa dal verbo (§4.5), che sa portare la conferma dei prezzi bundle. Il PATCH su valido_al era una seconda strada per la stessa scrittura, e su un legame con prezzi riceveva un avviso (E_BOM_CHIUSURA_CON_PREZZI) che non poteva confermare.

Per cambiare i valori: chiudere il legame (§4.5) e inserirne uno nuovo (POST §4.2). Sono due chiamate, senza un endpoint atomico. Le regole della fine (E_BOM_CHIUSURA_RETROATTIVA, E_BOM_LEGAME_CHIUSO) le dà il verbo, sul campo valido_al.

4.4 Elimina componente — RITIRATO (2026-11-09)¶

Il DELETE di un legame non esiste più (BE11 di brief-db-revisione-catalogo): la distinta è una storia, e il trigger d'immutabilità rifiuta ogni cancellazione. Un legame si chiude (§4.5). Dal 2026-11-10 la rotta non esiste più (§4.3).

4.5 Chiudi un legame, coi suoi prezzi bundle (2026-11-10)¶

Un prezzo bundle (vendite.listini_righe_componenti) vale solo finché il componente è nel kit. Chiudere il legame chiude anche i prezzi che vanno oltre la fine, o li toglie se stanno in una bozza e cominciano dopo, e da quella data il prezzo del kit in quei listini scende. Per decisione di Tid (Q19-Q22 di brief-db-revisione-catalogo) questo non succede in silenzio: la chiusura si conferma. Il giro è quello dell'annullo con legami:

  1. POST …/chiudi/ senza prezzi_confermati. Se il legame non ha prezzi da toccare, si chiude subito.
  2. Se ha prezzi: 409 E_BOM_CHIUSURA_CON_PREZZI, con ui_action = confirm_and_retry e campo valido_al. Il frontend apre la finestra.
  3. GET …/chiusura/?valido_al= elenca i prezzi e dà il numero (prezzi).
  4. POST …/chiudi/ con prezzi_confermati = quel numero. Se nel frattempo i prezzi sono cambiati, la risposta è di nuovo il passo 2, coi numeri aggiornati.

4.5.1 I prezzi che la chiusura tocca¶
Metodo GET
URL /api/v1/catalogo/articoli/{articolo_id}/componenti/{comp_id}/chiusura/?valido_al=AAAA-MM-GG
Sorgente vendite.fn_prezzi_legame_oltre_la_fine

Risposta: { valido_al, prezzi, righe[] }. Per ogni riga ci sono riga_id, listino_versione_id, listino_id, listino_codice, codice_versione, stato_versione, valido_dal, valido_al, prezzo, importo_per_kit (prezzo × coefficiente del legame), attivo, nel_perimetro ed esito:

esito Il prezzo…
CHIUDE comincia entro la fine: prende la stessa fine
TOGLIE comincia dopo la fine, in una bozza: si cancella
BLOCCA comincia dopo la fine, in una versione non in bozza: la chiusura si rifiuta

⚠️ Un prezzo in un listino che chi chiama non vede arriva con nel_perimetro = false e tutte le altre colonne vuote: si sa solo che c'è. prezzi è il numero delle righe, ed è quello da dichiarare. Se ci sono righe BLOCCA o fuori perimetro, il verbo rifiuta prima di confrontare il numero.

4.5.2 Chiudi¶
Metodo POST
URL /api/v1/catalogo/articoli/{articolo_id}/componenti/{comp_id}/chiudi/
Verbo DB catalogo.fn_chiudi_legame_distinta

Body: { "valido_al": "AAAA-MM-GG", "prezzi_confermati": 2 } (prezzi_confermati va omesso al primo tentativo). Risposta: { componente, prezzi_chiusi, prezzi_tolti }: componente è la riga come la dà §4.1.

Il backend non giudica niente: verifica solo che il legame sia dell'articolo del percorso (404 E_CATALOGO_COMPONENTE_NOT_FOUND) e che i due campi abbiano la forma giusta (400 E_CATALOGO_VALIDATION, col campo). Il resto lo dice il verbo:

Codice Quando
E_BOM_CHIUSURA_CON_PREZZI (409, confirm_and_retry) Ci sono prezzi da chiudere o togliere, e la conferma manca o non corrisponde
E_BOM_CHIUSURA_PREZZI_ALTRE_AZIENDE (409) Ci sono prezzi in listini che chi chiude non vede
E_BOM_CHIUSURA_PRIMA_DEI_PREZZI (400) Un prezzo di una versione non in bozza comincia dopo la fine: il messaggio dice la prima fine ammessa
E_PERMESSO_NEGATO Manca il livello TUTTO sul catalogo, oppure sui listini quando ci sono prezzi
E_BOM_LEGAME_NOT_FOUND, E_BOM_LEGAME_CHIUSO, E_BOM_CHIUSURA_RETROATTIVA Il legame non c'è, è già finito, oppure la fine è prima di ieri

Prove: apps/catalogo/tests/db/test_chiusura_legame_prezzi_db.py (sul DB vero) e il pgTAP catalogo/test-chiudi-legame-con-prezzi-v1.

  • ⛔ Nessuna nota di riga: una nota di catalogo annota l'articolo o il legame interi (CHECK chk_note_catalogo_ancora_documento). anchor_tipo è DOCUMENTO per difetto; RIGA, o un target_riga_id, sono un 400 E_NOTA_VALIDATION col campo anchor_tipo, prima del DB.
  • Una nota si scrive anche su un articolo o un legame spento, e non impedisce di spegnerli (Q12: la nota è un'eccezione dell'automazione ATTIVO).
  • ⛔ Il legame dev'essere dell'articolo dell'URL, su ogni verbo: articolo inesistente → 404 E_CATALOGO_ARTICOLO_NOT_FOUND, legame inesistente o di un altro articolo → 404 E_CATALOGO_COMPONENTE_NOT_FOUND, prima di leggere o scrivere le note (cancello del padre della factory; dal 2026-10-21).
  • Una nota di un altro padre dall'URL di questo: 404 E_NOTA_NOT_FOUND. Un articolo che non c'è, sulla lista o sulla creazione delle sue note: 404 E_NOTA_PARENT_NOT_FOUND.

6. Conversioni UoM¶

6.1 Lista conversioni¶
Metodo GET
URL /api/v1/catalogo/conversioni-uom/

Query param¶

Parametro Tipo Obbligatorio Descrizione
search string No Ricerca libera (colonne dal catalogo della lista catalogo.conversioni_uom)
attivo bool No Filtro attivo/disattivo
uom_id int No Filtra le conversioni con uom_id come from o to
limit int No Default 25, max 200
offset int No Default 0
order_by string No uom_from_codice (default), uom_to_codice, fattore, valido_dal, valido_al (il vuoto va come il massimo, lo dichiara il catalogo), attivo
order_dir string No asc/desc. Assente: asc su ogni colonna, date comprese (dal 2026-11-24 nessuna colonna ha un verso di partenza proprio: la regola «le date partono desc» è ritirata)

Risposta: envelope di lista {count, results} (pagina_con_totale, api.md §Paginazione): non è la lista completa. Dal 2026-11-11 la lista legge la vista catalogo.vw_unita_misura_conversioni_dettaglio (la vista_sql della lista 22) e ogni riga porta la stessa capability del §3.1 (puo_eliminarsi, motivo_non_eliminabile, puo_cambiare_attivo, puo_chiudersi, data_min_chiusura, data_default_chiusura, motivo_non_chiudibile).

6.3 Crea conversione¶
Metodo POST
URL /api/v1/catalogo/conversioni-uom/

Body JSON¶

Campo Tipo Obbligatorio Descrizione
uom_from_id int Si UoM sorgente (immutabile dopo create)
uom_to_id int Si UoM destinazione (immutabile dopo create)
fattore decimal Si Fattore di conversione > 0
valido_dal date No Fase 4: opzionale, fallback today se omesso/null
valido_al date No Limite superiore validita' (default null)

Una conversione vale per la coppia non orientata e il periodo: kg→g e g→kg in periodi che si sovrappongono sono la stessa conversione, e la rifiuta ex_unita_misura_conversioni_coppia_no_overlap (400 E_CATALOGO_VALIDATION). Fra unita' di tipologia diversa: E_UOM_CONVERSIONE_TIPO_DIVERSO dal DB.

6.4 Aggiorna conversione¶
Metodo PATCH
URL /api/v1/catalogo/conversioni-uom/{conv_id}/

Regole specifiche¶

  • uom_from_id, uom_to_id, fattore e valido_dal sono immutabili dopo create: li ferma il lock di colonna (E_UOM_STORIA_IMMUTABILE, col campo), e il detail li dichiara in non_editable_fields. Si cambiano valido_al e attivo, nei limiti della capability (§6.2); per valori nuovi si chiude e se ne inserisce una nuova.

7. Unita` di misura e tipologie (anagrafica)¶

Le UoM operative di un articolo stanno al §3; qui c'e' l'anagrafica delle unita` di misura e delle loro tipologie, che vive per conto suo.

⚠️ Per leggerle in una combo non si usano questi endpoint ma il lookup generico: GET /api/v1/core/lookup/codici/?rel=catalogo.unita_misura (oppure ?rel=catalogo.uom_tipi). Questi servono a manutenerle.

7.1 Tipologie UoM¶
Lista GET /api/v1/catalogo/uom-tipi/ — search, attivo, limit, offset, order_by, order_dir
Crea POST /api/v1/catalogo/uom-tipi/ — codice, codice_interno, descrizione (tutti e tre obbligatori)
Dettaglio / aggiorna GET PATCH /api/v1/catalogo/uom-tipi/{tipo_id}/

⛔ In PATCH sono modificabili solo descrizione e attivo: codice e codice_interno sono la chiave con cui il resto del sistema nomina la tipologia, e non si rinominano da API.

7.2 Unita` di misura¶
Lista GET /api/v1/catalogo/unita-misura/ — stessi query param del §7.1
Crea POST /api/v1/catalogo/unita-misura/ — codice, descrizione, tipo_uom_id obbligatori; descrizione_fattura opzionale
Dettaglio / aggiorna GET PATCH /api/v1/catalogo/unita-misura/{uom_id}/ — modificabili descrizione, descrizione_fattura, tipo_uom_id, attivo
Disattiva POST /api/v1/catalogo/unita-misura/{uom_id}/disattiva/ — body vuoto

⛔ Anche qui il codice e' immutabile dopo la creazione.

⚠️ La disattivazione puo' essere rifiutata dal database, ed e' giusto cosi': se esistono entitacollegate ancora attive l'IntegrityErrordiventaE_CATALOGO_VALIDATIONcon «esistono entita' collegate attive». Una UoM disattivata sotto i piedi di righe listino, magazzino e documenti che la puntano sarebbe un dato rotto, non una comodita. Se l'unitanon esiste (o era gia disattivata): E_CATALOGO_UOM_NOT_FOUND.

Entrambe le liste sono is_search_endpoint (throttling di ricerca) e dichiarano lista_codice — catalogo.uom_tipi e catalogo.unita_misura — con permesso di livello oggetto sui rispettivi modelli.

Regole trasversali¶

  • Tutti gli endpoint richiedono JWT.
  • La ricerca libera delle liste (search) cade sulle colonne che il catalogo della lista accende, con la soglia del catalogo: sotto soglia il termine non filtra, senza 400. Solo il lookup articoli (§2.1) risponde 400 E_SEARCH_VALIDATION sotto 3 caratteri (require_min_search_length).
  • Liste paginate (articoli, UoM operative §3.1, tipologie UoM, unità di misura, conversioni, distinta §4.1-bis, note §5): limit/offset, default 25, max 200; senza order_dir la colonna chiesta va in crescente, date comprese (la regola «le date partono desc» è ritirata dal 2026-11-24); il default di ogni lista resta il suo.
  • non_editable_fields: string[] (Fase 5) sta su: dettaglio articolo, envelope lista/lookup UoM operative, riga di create/update UoM operativa, dettaglio conversione. Non c'è su dettaglio unità di misura, dettaglio tipologia UoM, create/update componente. Il FE pilota i :disabled da questa lista invece di cablare regole. Source: vista dbops.vw_non_editable_fields (il lock vivo), letta dal BB compute_non_editable_fields. ⛔ Nessun gap Python: _NON_EDITABLE_DB_GAPS è ritirato il 2026-11-11 (BE21-a), dal giorno in cui il DB dichiara anche unità, fattore e inizio di mappature e conversioni.

Codici errore (404 NOT_FOUND)¶

  • E_CATALOGO_ARTICOLO_NOT_FOUND
  • E_CATALOGO_UOM_NOT_FOUND
  • E_CATALOGO_COMPONENTE_NOT_FOUND
  • E_NOTA_NOT_FOUND, E_NOTA_PARENT_NOT_FOUND (note, §5: i codici del BB delle note; E_CATALOGO_NOTA_NOT_FOUND non lo solleva piu' nessuno dal 2026-11-11)
  • E_CATALOGO_CONV_NOT_FOUND
  • E_CATALOGO_UOM_TIPO_NOT_FOUND (tipologia UoM)

Codici errore (400 VALIDATION)¶

  • E_CATALOGO_VALIDATION (catch-all dominio)
  • E_DATA_AL_MINORE_DAL (propagato dal guard comune delle date script.trgfn_guard_date_validita quando chiudi_al < valido_dal; fino al 2026-09-24 rispondeva E_BOM_VALIDO_AL_INVALIDO, ora ritirato)

Pattern view¶

I POST usano handle_post_json(...). L'header Idempotency-Key lo richiede solo il POST delle note (§5, dal BB delle note); gli altri POST del catalogo non lo chiedono. Le PATCH leggono il corpo con corpo_oggetto(request).
